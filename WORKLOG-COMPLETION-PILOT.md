- Separate API attempts from the copy/export ledger. Before POST persist pending by exact signature, without fabricating a manual handoff. A definitive refusal atomically replaces pending with a retryable, open “Tempo refused” state and an in-app reason. Mark entered for a refused signature requires its genuine copy/export or successful read reconciliation. Manual corrections overwrite provenance as manual, retaining the remote ID for duplicate guards. - Precedence for current lines is open correction first, then valid confirmed coverage, then unknown pending or read status, refusal, approved/ready, and draft. Never override an earlier confirmed receipt on read failure. Exact matches must be unambiguous and cannot reuse a Tempo ID known to cover another line. A read-only check shows unmatched remote time on relevant issues for review, including near matches, without claiming verification. A successful no-match read may clear a transient read failure but holds a pending POST for the existing explicit resend decision. Preserve the current same-issue overlap warning and capture signature check immediately before a write. Test refusals, copied/exported states, lost reply and no-match read, authentication failure after a partial success, reused IDs and rounding-mode switches.

## Implementation decisions

- The cutoff defaults to 18:00 and is fixed at baseline enrollment. The timer uses a 15-second continuity window and timestamps the observed snapshot. Relevant local writes check the cutoff before mutating the ledger. If there is no on-time observation, the day stays in the eligible-workday denominator when the user confirms they worked. Pilot closure includes explicit manual attestations. The report also splits verified-only closure, closure with an attested worklog and closure with no required worklogs.
- API sends no longer write either `RecordExport` or `RecordHandoffKeys`. Existing handoff history is retained for repeat warnings. Older copy/export keys cannot establish a genuine copy after a refusal. An old local ledger record without receipt provenance is treated as manual unless the app can match the original Tempo ID and line. A prior unconfirmed send remains pending if a later resend is refused. HTTP 408 is treated as uncertain for writes.
- A read-only status check holds ambiguous exact matches and shows unmatched time for relevant issues. A detached pending send remains open across line edits and rounding-mode changes. It can be reconciled against the saved line or explicitly cleared after a successful no-match read and manual verification.
- The first Windows 11 smoke pass used a real legacy Shell balloon and an explicit standby registration. The operator confirmed that the banner appeared and timed out before they could click. The revision below replaces that adapter and leaves dated navigation, receipt semantics and the pilot measurements in place.

## Notification Center revision for re-review

- On Windows 11, the user saw the synthetic Shell banner but it timed out before they could click. Windows 11 discards legacy tray balloons at banner timeout. Replace that adapter with the supported Windows app notification API for unpackaged WinForms. Use a normal, non-modal notification with generic text and an explicit Review worklog action. The toast can remain in Notification Center after the banner duration. The tray summary remains available if Windows silences or cannot register app notifications. Keep only one submission to Windows per reserved cue. [Windows 11 legacy balloon behavior](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-shell_notifyiconw) · [App notifications for WinForms](https://learn.microsoft.com/windows/apps/develop/notifications/app-notifications/app-notifications-dotnet)
- Give each toast an opaque token and a distinct tag. Pass the same token and tag from the toast body and the Review button. The adapter binds them to the live app’s date and cue kind. Validate both values, the date, session, settings and app-side deadline before routing, on the app UI thread. Use Windows native expiry and expiry on reboot. Remove the exact toast on activation, skip, snooze, opt-out, closure, expiry or clean exit. Legacy balloons are removed from the completion adapter.
- Bound the action to the lifetime of the running tray session. Restart preserves date-scoped issuance and prevents another unsolicited cue. After a crash or restart, Windows may still have a stale toast. A cold COM notification launch is discarded before the ordinary startup/mutex path and never triggers its generic ShowExisting message. An opted-in normal startup registers on the new process and clears leftover completion toasts before new issuance. The private tray summary is the route after restart. Unknown and stale activations in an already running session are ignored. There is no pilot exposure credit from any of those paths.
- Use `AppNotificationManager` from the stable Windows App SDK with unpackaged, self-contained output. Set the Windows TFM for the app and test host, bundle required app-local components, and avoid mandatory bootstrap or deployment registration at app entry. Subscribe to activation before registration. Load the adapter only when opted in and treat unavailable support, disabled settings or COM and runtime errors as a tray-only fallback. Synthetic smoke tests have a separate executable identity and clear their synthetic toast and registration on exit.
- Repeat the automated suite and synthetic Windows path. Verify a toast remains in Notification Center after banner timeout and opens its date when activated within expiry. Check stale, duplicate, opt-out and unavailable-registration paths. Record the Windows call, valid app activation and user-visible outcome separately. Windows does not give the app a reliable visibility or dismissal signal for this API.
