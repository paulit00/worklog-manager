# Worklog Desk architecture

A low-resource Windows tray app that turns a Business Central DevOps workday into reviewed Tempo worklogs. It uses Jira Cloud for issues and Tempo Cloud for time. Description is the only additional field required by the user's form. Five minutes can book as 15. The company rule for combining repeat work on one issue is still unknown.

## Delivery checkpoints

| Checkpoint | Build and finish criteria |
|---|---|
| A0a · Offline capture | A pure reducer, versioned SQLite store and CSV. Replay synthetic input and prove recovery, exclusion and balanced elapsed totals before UI work. No credentials. |
| A0b · Review | Tray, manual timer, task pin, quick request capture and editable daily review. Complete the 12-row keyboard demo against a bundled fake issue catalog. In a real offline trial, assign by client/task or type a provisional issue key. Live issue validation begins in A1a. In a separate three-day shadow trial, compare with the user's manual log and measure incorrect assignments, unassigned share, idle gaps, individual short approvals, corrections and review time. Target zero known wrong automatic assignments and under three minutes median review. Disable and recheck any faulty rule. |
| A1a · Jira and manual Tempo | Search and link Jira issues, including colleague-owned Waiting for Customer issues. Link missing-ticket drafts through the normal create form. Copy or export approved lines for manual Tempo entry. Finish with read-only Jira and fake Tempo. |
| A1b · Approved Tempo writes | Implement the confirmed live grouping mode. Enable writes after the shadow trial, rounding confirmation, fake fault tests and a permitted test-project rehearsal. |
| B · Attribution and Jira creation | Improve shared browser and workspace attribution. Add approved Jira and JSM draft creation using project metadata. Each improvement can ship independently. |
| C · Outlook | Add selected-day sent-mail and calendar suggestions. Teams works through pasted request links and the manual timer from A0b. Revisit chat import or MCP if that workflow leaves a measured gap. |

**Layout.** `WorklogDesk.Core` is pure .NET 10. `WorklogDesk.Windows` owns WinForms, Win32 adapters, SQLite, credentials and HTTP. Keep I/O off capture callbacks and network work off the UI thread. Tests use a synthetic clock, Windows event replays, temporary SQLite and versioned HTTP fixtures. A browser helper is optional and only ships after B's experiment.

**Launch.** Use an untrimmed, framework-dependent .NET 10 Desktop Runtime build. If the runtime is unavailable, test an approved self-contained per-user package against the same budgets. Use the company's signing or allowlisting process if required. Otherwise use the manual workflow on an authorized machine. Use a current-user ACL on a `Global\WorklogDesk.<SID>` mutex so only one process owns capture and posting across local Windows sessions. A later same-session launch signals the owner over a current-user pipe to open review. If the owner is in another session, show its status without starting a second capture. Test simultaneous launch and recovery after owner exit.

## Capture and review

First launch starts paused. The user opts into work app families and optional start at sign-in. Restarts restore the last explicit run/pause choice, subject to normal lock/idle rules. Show a persistent paused state and a workday reminder if configured. The tray shows recording state, active pin and days needing review. **Review**, **Pin task**, **Capture request**, **Assign last RDP span**, **Start/stop manual timer** and **Pause** are always reachable. Configurable Ctrl+Shift+Alt shortcuts report registration conflicts. A quick request takes a one-line summary, optional client and a pasted Teams or Outlook link. A note alone works.

| Signal | Capture rule |
|---|---|
| Foreground change | Use WinEvents in the opted-in, unlocked, awake session. Check foreground and idle every five seconds. Discard obsolete events. A missed focus change closes at the last trustworthy sample and leaves a gap. |
| Idle and passive work | Default to two minutes, editable per app. Trim eligible foreground fragments after the last input in the same uninterrupted capture run. Do not trim manual timing or an earlier run. Keep the trimmed gap available for reading, calls or supervised AI. An idle-lookback tail stays provisional across app switches and midnight until settled or explicitly confirmed. |
| Pause, lock, disconnect, sleep or exit | Close the span and clear transient source state. The manual timer replaces foreground time and survives ordinary inactivity. Unattended background execution while doing other work contributes no simultaneous duration. |
| Crash | Checkpoint every 30 seconds. Close at the last durable sample, keep any provisional tail editable and show the gap until the first trustworthy new sample. End a recovered manual timer at that checkpoint and offer Resume now. Let the user confirm actual gap time separately. No downtime accrues automatically. |
| Clock shift | Use monotonic elapsed time anchored to UTC. Reanchor after a jump over five seconds. Store contested raw UTC positions in separate epochs. Keep overlaps across epochs unresolved until the user can place or exclude them. Approved intervals cannot overlap. |
| Pin and conflict | Exact configured client aliases and trusted Jira issue keys are strong evidence. An approved client alias identifies only the client. Leave the issue unassigned without an exact trusted key or a valid explicit issue pin. Generic app names and recent choices are suggestions. Contradiction with a pin makes a review row, across every source. Suspend a pin when the app enters idle. If still idle five minutes later, expire it. For example, the two-minute idle default suspends at two minutes and expires at seven. Before expiry, resume only on a matching client/task or user confirmation. |
| Short switches | Under ten seconds with no confirmed competing task is incidental. Preserve it in captured and excluded totals, with zero workday credit or billing. It does not split the task. A standalone billable group with less than two minutes of actual work needs individual approval. Short fragments already joined into a reviewed group do not need separate approval. |

**Source rules.** Inspect window titles and labels only in memory. Store only the app family and approved canonical alias or key.

- **RDP** · Match a configured alias from a supported `mstsc` or `msrdc` connection label in memory. Pin before fullscreen on shared gateways, or assign the last RDP span afterward. Unsupported clients need manual assignment. No inspection inside the session.
- **VS Code and AI** · Use exact workspace aliases. Unrecognized terminals need a pin. B can add an opt-in workspace picker or tool hook for a validated branch Jira key. Record no raw paths, commands or chats.
- **Browser** · Off by default. Process-only timing records **Browser** with explicit consent and no host claim. Test exact Edge profile aliases in A0b without an extension. An alias is a client clue. With B host filtering enabled, capture only a verified approved work tab. Unavailable identity clears attribution and leaves manual timing available.
- **Outlook and Teams** · Use pasted links and a manual call timer first. A link or sent timestamp suggests a client or task without adding duration.

**Daily review.** Show three totals above the queue: reviewed actual time against target, time needing attention and proposed/posted time. Expand for captured, internal, excluded, rounded and verified coverage detail. Set the target by weekday with a per-date override for holidays or leave. The default queue prioritizes unassigned rows and held/late work. Split, merge, reassign or exclude allocations without changing the raw timeline. Offer reusable mappings only after explicit approval. Local internal time counts toward completeness and posts only if the user assigns a configured internal issue.

Build a billing session after assignment, across tools. Same-task fragments with up to two minutes of gap may join, with the gap contributing zero seconds. A competing task, conflict, explicit break or longer gap ends the session. Freeze approved session membership and rules. For the demo, include same-issue app switches, a shared RDP conflict, a colleague's Waiting issue, a new request, an incidental switch and a call. Target two minutes on the demo separately from the shadow-trial target.

## Review and post to Tempo

1. **Find the issue.** Support My active and Waiting issues, exact-key lookup, and paginated text/status/assignee search across mapped client projects. Include unassigned and colleague-owned issues. If no ticket matches, open the appropriate Jira/JSM create form and copy the draft summary on request. Link the resulting key. B adds approved API creation using required issue fields or JSM request type and permissions. Preview customer-visible text and recipients. Keep private links local.
2. **Close the day.** The user explicitly closes a review snapshot. Settle or visibly defer the open timer, provisional tails and unassigned work. A held row that could change an issue/day total also holds that issue group. Late capture appears separately. A workday is a half-open UTC interval from a frozen local timezone. Split actual time at midnight and preview both dates, including any rounding uplift. Confirm how company policy treats an affected overnight batch.
3. **Confirm rounding.** A0 shows both issue/day and per-session totals, with issue/day the display default. No default authorizes live posting. The user or company billing owner confirms grouping and the overnight rule before the A1b enablement review. Continue with A1a manual assistance while that answer is pending. Store the confirmed unit (900 seconds), rounding rule, grouping, timezone and boundary revision. In the upward preview, 5→15, 15→15 and 16→30. Two sessions of five and seven minutes show 15 versus 30. Highlight uplift and keep actual seconds unchanged.
4. **Check the payload.** Grouped entries have one editable Description. Suggest an explicit request summary or the Jira issue summary and reject blanks. Notes remain local. Prefer a date-only issue/day worklog if the tenant rehearsal confirms the intended behavior. Otherwise use the earliest actual fragment as the nominal start. Never invent a start. Preview timestamped ranges against proposed and existing worklogs that intersect the date, including previous-day spillover. Use one batch acknowledgement if overlaps are permitted. Hold incompatible ranges or repeated-hour timestamps that Tempo cannot distinguish. Let the user pick a legitimate actual anchor. If the tenant supports neither date-only logging nor the required overlaps, keep the affected groups in assisted mode with Copy details and manual Tempo completion. Accept that fallback in the rehearsal before enabling production. Do not invent an anchor to force an API write.
5. **Reconcile existing time.** Inventory the user's remote worklogs. Reuse confirmed IDs only when author, issue, date, normalized start when used, duration, Description and `updatedAt` match. Ask only about unknown same-issue entries that could cover this group. An edited known ID triggers a reverify row. After the user confirms it still covers the intended work, bind its revised duration and update time as C. Clear a partial-coverage hold only when the verified total satisfies the target. A remote ID covers one group. With target T and verified coverage C, write T for uncovered groups, zero when C ≥ T, and hold partial coverage (0 < C < T) with the exact manual difference. Never round a remainder independently.
6. **Post and handle late work.** Post only the approved payload. Show each operation state in the same review. In issue/day mode an existing confirmed issue/day is single-write. Late work on a different uncovered issue may create a new group. In session mode, reopen the existing issue/day reservation for a new independent session only after a fresh inventory and resolution of any prior holds. Use a new session ID and never reclaim a previously approved allocation. For all confirmed groups, including this app's own posts, the user makes corrections manually in Tempo. The app only creates new uncovered worklogs. It never calls Tempo update/delete in A1. Copy the proposed change and verify the result on refresh. For instance, 5 actual minutes booked as 15 plus 11 late minutes makes a 30-minute target and a +15 correction. If existing rounding covers the new actual time, record coverage locally without sending another description. In session mode, show a correction if new evidence bridges two confirmed sessions. For example, two five-minute logs already booked as 30 plus a three-minute gap proven to be the same task recompute to one 13-minute session and 15 booked. Keep both remote IDs linked to their immutable original groups while reviewing the -15 day-level correction. Change the coverage links only after the user reconciles both records in Tempo. No automatic merge or new write. Offer **Copy details** and CSV for manual entry.

### Connections

- **Jira Cloud** · Verify `/myself` and use enhanced JQL with escaped filters. Bind account and site separately from the API origin. Use the Atlassian gateway and cloud ID for scoped tokens, or the site for permitted unscoped tokens.
- **Tempo Cloud v4** · Use a separate Worklogs-scope token, the universal or explicitly chosen documented regional origin, and a read-only worklog search filtered by Jira account ID. Before using new or rotated credentials, cross-check an existing same-account test-project worklog using Jira/Tempo ID mapping, issue, author and duration. If there is no sample yet, the user can create one in the Tempo UI. This read-only check binds the pair before the first app write. Send issue ID, author, date, optional start, approved seconds and Description. Leave billing/estimate fields alone unless the observed tenant behavior and approved setting require them. Never override locked periods, change issue status or submit the full timesheet.
- **Rehearsal** · After the read-only credential check, explicitly authorize one 900-second app write in a test project and verify its Tempo readback, author and Jira issue. Confirm status, permissions, Description, estimate and date/overlap behavior. Only then permit production posts. A denied Waiting issue or closed period retains the work and provider reason. Read errors, expired tokens or identity mismatch pause writes. Use fake mode and export if access is unavailable.

### Durable posting contract

Use a unique reservation for site, author, issue and day. Freeze the day policy, approved membership and payload in one transaction. Each allocation ID can belong to one operation. In session mode, the reservation owns sibling operations sent serially. Recheck remote assumptions before each send and reopen affected Prepared work when outside changes occur. Own confirmed writes advance the expected snapshot. A local lock cannot control other Tempo clients. After each batch, refresh the affected day and surface new matching records as a possible duplicate for manual comparison and correction.

| Stored state | Next action |
|---|---|
| Prepared | Cancel, or commit Sending before the request after a fresh coverage check. |
| Sending | A matching success with remote ID becomes Confirmed. A proven no-write throttle becomes Deferred. A definitive validation denial becomes Rejected. Lost response, cancellation after dispatch, malformed result, 5xx or restart becomes Needs verification. |
| Deferred | Honor Retry-After. Resume the same approval after fresh checks. Unclear throttling is Needs verification. |
| Confirmed | Lock approved allocations. A readback mismatch holds the affected group pending verification. |
| Rejected | Release the line's claim. Retain the issue/day reservation for outstanding siblings. Correct and reapprove if no coverage conflicts. |
| Needs verification | Hold the line and siblings. Show new matching candidate IDs and link only a verified existing record. No repeat create while uncertain. Provider audit or support can confirm non-commit and allow a fresh approval with its reference recorded. Otherwise provide a practical manual route: refresh the relevant Tempo day, show exact candidate comparisons, and open the official Tempo view. If the user chooses to finish there after checking for a match, show the residual duplicate risk, record the decision, and require a verified Tempo ID before marking the line covered. Keep the original reservation and disable in-app resend throughout. An empty result alone cannot release the hold. |

Stop unrelated groups only for connection/account errors or a shared changed assumption. Restore Prepared, Sending and Deferred as uncertain. On restore or rebuild, persist a ledger epoch and the first full local workday beginning after that epoch. A genuinely new day captured wholly after that boundary follows ordinary coverage checks if its local operation history is complete. A backdated, imported or recreated day without complete history enters reconciliation, even if it was created in the app after the rebuild. Any workday presented for posting needs manual verification if its ledger is incomplete, including a newly recreated day with no surviving operations and a backdated post made after the snapshot. Link verified remote records for coverage. On restored dates with incomplete history, use a provider-authoritative write history or support attestation to clear a missing historical write. A verified existing ID resolves coverage without any new write. Hold if the result is uncertain. A fresh empty read is insufficient. Use the same hold for uncertain Jira/JSM creation. Ordinary Jira can provide a random operation property read directly from bounded recent issue candidates. JSM recovery verifies the existing issue before preparing a Tempo entry. Bind credentials and pagination to the configured HTTPS origin and API path. Disable redirects. Retry only read-only calls automatically.

## Storage and integration checks

**SQLite.** Under current-user-restricted `%LOCALAPPDATA%\WorklogDesk`, outside installation. Use WAL, a single logical writer and parameterized migrations/queries. Store raw span epoch/times and one checkpoint, allocations keyed by ID and indexed by date, mappings/drafts, frozen day policy, unique reservations, operation payload/state/remote ID, and unique site/Tempo ID coverage. No overlaps in approved allocations or within one raw monotonic epoch. Protect private notes, links and descriptions with DPAPI and tokens with Credential Manager. Retain raw evidence 30 days. Keep approved time until deletion. Back up reviewed data without tokens or raw evidence to a current-user-restricted Backups subfolder in the data directory. DPAPI-protected fields restore only when decryptable under the original Windows user profile, ordinarily on the same device. If verification or decryption fails, leave the archive read-only and reconcile a new local ledger against Tempo. Opt-in traces export relative event timings and rotating IDs, without customer data. CSV omits source data and escapes formula-like fields. Use SQLite secure_delete for retained evidence and private rows, then truncate WAL on purge. Treat this as local cleanup rather than physical-erasure certification. Release updates as a versioned per-user app folder through the approved internal channel. Exit and back up before replacing binaries. Keep data outside the install folder and migrate it transactionally. Uninstall offers separate data and token cleanup.

**Browser gate.** Timebox A0b profile detection separately from B. For B, compare a focused-profile report with foreground-epoch/unique DPI-correlated snapshots. Require correct results across real Chrome/Edge windows, profiles, mixed DPI, BC tenant changes and rapid focus switches. Invalidate on navigation, blur, lost connection or permission change. Prefer the simplest passing bridge. Request configured host access only and send canonical BC tenant/environment, Azure DevOps org or Jira key over a bounded current-user pipe with publisher validation. No raw URL/title recording. Check managed installation and allowlisting. Require p95 eligible refocus under 500 ms and no wrong assignments before enabling.

**Outlook gate.** On-demand delegated Graph `Mail.ReadBasic` and `Calendars.ReadBasic`. Match selected-day recipients transiently. Retain timestamps, deduplication digests and matched client IDs. Skip private items. Ask for attendance and resolve overlaps before adopting meeting time. Mail alone cannot decide between multiple issues. Confirm actual authorized fields and denial fallback.

**Release evidence.**

- **A0a:** lock/sleep, missed events, cross-midnight provisional tails, backward-clock epochs, capture/manual crash recovery, no duplicate ownership, exclusion and exact export totals.
- **A1 before first live write:** versioned fake contract, account mismatch, atomic reservation, coverage arithmetic, partial batch, timeout after commit, restored older backups (backdated and Deferred sends, plus clean future days versus recreated historical work), pre-send remote changes, a concurrent Tempo entry after the last read, an empty search that must not release a held operation, an audited release, an operator-manual resolution, an edited known worklog, and the confirmed sample. Before enabling affected cases, test DST, cross-day overlaps and session siblings. Use known fixtures and fault injection.
- **Resources:** .NET Release, 60 seconds warm-up plus 60 seconds idle. At A0b gate tray private working set <60 MiB and <0.5% of one logical core. At B gate tray + bridge private working set <80 MiB. Added browser private working set ≤16 MiB and idle CPU ≤0.25% of one logical core compared with the same browser without the extension. No idle HTTP. Render 1,000 intervals in <500 ms. At 10 switches/sec for two minutes, p95 event processing <50 ms. Synthetic 10,000-span DB+WAL growth <5 MiB after normal checkpoint. Report hardware and actual readings, and withhold optional enhancements that fail the laptop budgets.

## Operational decisions

- Freeze the company worklog timezone for a workday. Use the Jira profile timezone as the initial suggestion and verify it against Tempo in the rehearsal. Windows travel/timezone changes do not remap stored work. Hold a posting if the provider timezone cannot be reconciled with its frozen policy.
- Show overdue days in date navigation. Before expiring raw evidence, retain its unresolved day totals and editable uncategorized allocations so the oldest day can still be reviewed without retaining title or source clues indefinitely.
- Keep same-device backups for 30 days. Local deletion also removes app-managed snapshots containing the deleted records. For approved off-device recovery, export a reviewed, redacted CSV to a user-chosen authorized location. Unexported, unposted work can be lost if the device is lost.
